# Database Design

---

# 1. Purpose

This document defines the database architecture of Learning OS.

It establishes:

- Collection structure
- Document ownership
- Relationships
- Naming conventions
- Data consistency
- Query strategy
- Scalability rules

This document serves as the single source of truth for every Firestore collection.

---

# 2. Database Philosophy

Learning OS uses **Cloud Firestore**, a NoSQL document database.

The design follows these principles:

- Normalize when practical.
- Denormalize only for read optimization.
- Avoid duplicate business data.
- Keep documents small.
- Optimize for reads.
- Design for horizontal scalability.
- Prefer document references over deep nesting.

---

# 3. Design Principles

## Single Source of Truth

Every piece of business data has exactly one owner.

Example

Mission Title

Owned only by

missions/{missionId}

Never duplicate it elsewhere.

---

## Flat Collections

Prefer

```
missions/
submissions/
resources/
```

Avoid deeply nested collections unless ownership requires it.

---

## Small Documents

Target

< 100 KB

Never approach Firestore's 1 MB document limit.

---

## Immutable IDs

Document IDs never change.

Business fields may change.

IDs never do.

---

## Server Timestamps

Every document stores

```
createdAt

updatedAt
```

Generated by the server.

# 7. Reference Strategy

Relationships use document IDs.

Example

```
missionId

studentId

resourceIds
```

Avoid storing duplicate objects.

---

# 8. Ownership Rules

| Entity | Owner |
|----------|---------|
| User | users |
| Mission | missions |
| Submission | submissions |
| Resource | resources |
| Announcement | announcements |

Every entity owns its own data.

---

# 9. Query Strategy

Repositories expose business queries.

Examples

```
getStudentMissions()

getPendingSubmissions()

getAnnouncements()

getResourcesForMission()
```

Avoid generic "getAll()" methods.

---


---

# 12. Data Validation

Validation occurs at three layers.

```
React

↓

Application Service

↓

Firestore Security Rules
```

Database validation is never skipped.

---

# 13. Deletion Strategy

Avoid hard deletion.

Preferred

```
status = archived
```

Future

```
deletedAt
```

This preserves audit history.

---

# 14. File Storage

Binary files belong in Firebase Storage.

Firestore stores only metadata.

Example

```
proofImage

↓

Storage URL
```

Never store images inside Firestore.

---

# 15. Auditability

Every important entity stores

```
createdBy

createdAt

updatedAt
```

Critical actions are recorded in

```
activityLogs
```

---

# 16. Security

Sensitive fields are protected using:

- Authentication
- Role-Based Access Control
- Firestore Rules
- Storage Rules

Never trust client-side validation.

---

# 17. Performance Strategy

Optimize for reads.

Rules

- Small documents
- Indexed queries
- Pagination
- Avoid duplicate reads
- Avoid loading entire collections

---

# 20. Database Rules

✓ One source of truth.

✓ Every document has an owner.

✓ IDs are immutable.

✓ Files belong in Storage.

✓ Documents remain small.

✓ Reads are optimized.

✓ Collections stay flat.

✓ Business logic never enters Firestore.
